# 远程 Obsidian、微信公网入口与 DeepSeek 处理设计

## 1. 背景与边界

Knowledge Manager 已部署在旧笔记本 Hyper-V 中的 Ubuntu 24.04。解析流水线、Obsidian 写入、微信客服协议基础、服务器一致性备份和第二物理盘复制均已有实现与实机证据。剩余工作是让 Windows 与安卓设备安全使用服务器 Vault、接通真实微信客服公网回调，并把归类、总结和提取从不合格的本地小模型迁移到 DeepSeek API。

本设计取代原先“部署本地语言模型”的后续方案。Qwen 2.5 1.5B 的长文事实覆盖验收已经失败，继续保持关闭；保留的模型文件不参与生产处理，也不再要求安装更大的本地语言模型。音视频转写仍使用服务器上的固定 Whisper 模型。

用户已明确批准：所有资料的解析正文、表格文本、OCR 文本和音视频转写文本都可以发送给 DeepSeek API。原始 PDF、Word、Excel、图片、音频和视频文件不发送给 DeepSeek。Ubuntu 保存完整原件、提取正文、转写、任务状态、API 结果和 Obsidian 笔记，是系统的完整主数据来源。DeepSeek 是外部处理方，因此“数据保存在旧电脑”不表示处理内容从未离开旧电脑；提供方对请求数据的处理仍受其账号设置和服务条款约束。

代码、部署脚本、测试、设计和验收记录全部提交到 `zhangyisequence-cell/Knowledge_Manager`。真实知识、账号标识、API 密钥、Cloudflare 凭据、微信 Token/AESKey、SSH 私钥、Tailscale 密钥、Syncthing 设备密钥和模型文件不得提交 Git。

## 2. 总体架构

系统保留四个相互隔离的入口和处理面：

1. **微信公网入口**：Cloudflare Tunnel 只把固定 HTTPS 主机的 `/wechat/callback` 转发到 Ubuntu 回环地址上的微信回调服务。
2. **知识处理面**：主应用从持久化队列读取已保存的原件，进行本地解析、OCR 和转写，再调用 DeepSeek API，最后写入 SQLite 和 Obsidian Vault。
3. **个人访问面**：Ubuntu、Windows 和安卓之间只通过 Tailscale 私网连接 Syncthing；不把管理 API、Vault、SSH 或 Syncthing GUI 暴露到公网。
4. **数据保护面**：服务器一致性归档、Syncthing 文件版本、Windows 第二物理盘副本和独立恢复演练分别承担不同层次的恢复责任。

公网微信入口与个人访问面没有共享认证或路由。Cloudflare Tunnel 不能访问管理页面，Tailscale/Syncthing 也不参与微信回调。

## 3. Obsidian 同步

### 3.1 拓扑与权限

Ubuntu 直接加入用户的 Tailscale 网络，并以 `knowledge-manager` 专用服务账户运行 Syncthing。只共享 `/srv/knowledge-manager/vault`，文件夹类型为 Send & Receive。Windows 和安卓分别以独立 Syncthing 设备加入；安卓采用维护中的 Syncthing-Fork，并用本机 Obsidian 打开同步目录。

数据库、队列、解析中间文件、运行配置、凭据、备份归档和模型缓存不进入同步文件夹。客户端仅获得 Obsidian 笔记及 Vault 内用于阅读笔记的附件。完整系统恢复始终以 Ubuntu 数据与已验证归档为准。

Syncthing 管理界面只绑定 Ubuntu 回环或 Tailscale 地址，并设置独立强口令。设备连接使用显式设备 ID；配置固定 Tailscale 地址，关闭公网端口映射。不会在 Windows 宿主机创建新的公网或局域网端口转发。

### 3.2 文件与冲突策略

Ubuntu 端启用 Staggered File Versioning，至少保留 30 天。客户端的删除和覆盖会正常同步，旧版本保存在 Ubuntu 的 Syncthing 版本目录中；版本目录本身不再同步给客户端。

同步 Vault 内容及通用 Obsidian 配置，但排除设备状态和临时文件，包括工作区布局、缓存、回收站临时内容、Syncthing 冲突之外的编辑器临时文件。具体忽略规则由仓库中的受测配置模板生成，不手工散落在三台设备上。

服务器写入的新知识只触发文件同步，不重新进入解析队列。客户端编辑同步回服务器，也不会被当成微信或上传任务。Syncthing 产生的 `sync-conflict` 文件必须保留并进入冲突检查结果，不能自动覆盖或删除；用户在 Obsidian 中合并后再清理。

### 3.3 同步验收

验收必须实际完成以下往返：服务器新建笔记到 Windows/安卓；Windows 修改到服务器/安卓；安卓新建与修改到服务器/Windows；删除后从 Ubuntu 版本历史恢复；两端离线编辑同一文件后生成可识别冲突；Ubuntu、Windows 和安卓重启或断网重连后收敛到相同文件散列。只看“已连接”状态不算通过。

## 4. DeepSeek API 处理

### 4.1 输入和配置

所有格式先使用现有本地适配器完成原件保存与确定性提取：网页正文、PDF/DOC/DOCX/Markdown 文本、Excel 单元格与公式标记、图片与扫描页 OCR、音视频转写。API 只接收这些文本结果及必要的来源位置标识，不接收二进制原件。

沿用现有 OpenAI 兼容客户端，生产配置使用：

- `AI_ENABLED=true`
- `KNOWLEDGE_OPENAI_BASE_URL=https://api.deepseek.com`
- `OPENAI_MODEL=deepseek-chat`
- `OPENAI_API_KEY` 仅写入 Ubuntu `/etc/knowledge-manager/server.env`

部署时先通过 DeepSeek 官方接口核对当时有效的基础地址、模型名、结构化输出行为和限制，再锁定验收记录中的实际模型标识。模型别名发生变化不得在没有复验时静默切换生产结果。

### 4.2 长文与证据约束

长内容按可追踪的来源区间分段，每段要求输出结构化 JSON：事实、人物或组织、时间、金额、事项、候选分类、标签、摘要要点和逐字证据。每条证据必须能在保存的提取文本中精确定位；无法定位的字段不得进入最终事实集合。

归并阶段对分段结果去重，保留来源区间，并检查文档开头、中间和结尾都已处理。最终摘要与分类只基于已验证的事实集合生成。任何段落失败、结构化结果无效、证据不匹配或分段缺失都会使任务保持失败或待重试，不能将不完整结果标为成功，也不能静默回退为“AI 总结”。

Obsidian frontmatter 和数据库记录实际提供方、模型标识、分析时间、完整/失败状态及来源证据，但不保存 API 密钥、Authorization 头或完整请求日志。用户已允许全部文本调用 API，因此不增加逐条选择开关；API 全局关闭时使用明确标注的规则整理，不能称为 DeepSeek 分析。

### 4.3 可靠性和费用边界

客户端设置连接、读取和总任务超时；对超时、连接失败、限流和服务器错误使用有上限的指数退避，并持久化下一次重试时间。鉴权失败、余额不足、非法请求和超过输入限制应快速失败并显示可操作原因。重启后继续未完成任务，同一任务重试不得创建重复知识条目。

请求按任务和分段记录 token/用量元数据以及成功或错误类别，用于成本和故障诊断，不记录正文。仓库只提供配置项和校验，不包含真实额度或密钥。

### 4.4 DeepSeek 验收

先用合成且可核验的中文长文验证开头、中间、结尾唯一事实、金额和日期，再验证真实格式链路。必须覆盖网页、PDF、Word、Markdown、Excel、OCR、音频和视频；核对原件、提取文本、请求分段、证据、最终摘要、分类、数据库与 Obsidian 笔记之间的一致性。若模型遗漏强制事实、引用不存在的内容或发生静默截断，AI 不得启用。

## 5. 微信公网入口

### 5.1 官方通道

采用企业微信的微信客服 API。回调只表示有新消息；服务器验签、AES 解密并持久化通知后快速返回，再由后台 worker 调用 `kf/sync_msg` 按游标取回文字、链接和媒体 ID。媒体先下载并原子保存到服务器，成功保存后才进入统一解析队列。

同一客服账号与消息 ID 组合用于幂等；只有客户消息和允许名单中的发送者能够创建知识任务。未知发送者保留最少的审计状态但不解析资料。同步页必须全部持久化后才能推进游标，空页仍遵循 `has_more`，重启后从保存的游标继续。

### 5.2 Cloudflare Tunnel

`cloudflared` 作为独立 systemd 服务从 Ubuntu 主动建立出站隧道。稳定主机名由服务器本地的 `WECHAT_PUBLIC_HOSTNAME` 配置，DNS 由用户的 Cloudflare 托管域提供。反向代理仅允许该主机的 `/wechat/callback` 到 `127.0.0.1:8766`；其他路径返回拒绝或 404。

回调入口只接受所需的 GET/POST 方法，设置请求体上限、速率限制和超时，关闭包含查询参数的访问日志。应用执行签名、AES、接收方、时间窗口及重复通知校验。Cloudflare 不能替代微信加密验证，也不能使用交互式 Access 登录阻断微信服务器。

知识库管理页面继续只监听回环地址；Syncthing、SSH、Vault 和数据库没有 Cloudflare 路由。路由器、Windows 宿主和 Ubuntu 不开放新的公网入站端口。

### 5.3 回复和平台限制

处理完成后，微信只返回任务编号、标题、分类、简短摘要和成功/失败状态，完整笔记通过用户自己的 Obsidian 同步查看。结果按发送者批次合并，遵守 48 小时内最多五次主动回复和 2048 UTF-8 字节限制；API 接受与最终送达分开记录。过期结果保留在服务器，不能生成公开知识下载链接。

实际账号配置包括企业 ID、应用 Secret、客服 ID、回调 Token/AESKey 和发送者允许名单，全部只存服务器。没有真实账号和稳定 HTTPS 域名时，可以完成代码及离线协议测试，但不能把微信标为已接通。

### 5.4 微信验收

真实允许名单用户依次发送文字、网页、PDF、Word、Markdown、Excel、图片、语音和视频，并收到对应结果。核对服务器原件字节、来源类型、任务状态、DeepSeek 结果和 Vault 笔记。重复回调、分页、断网、媒体过期、超限、回复失败、服务重启和游标续处理都须实测。模拟 HTTP 或公开加密向量只能证明协议代码，不能替代真实收发。

## 6. 备份、保留和恢复

### 6.1 三层保护

1. Syncthing 30 天版本历史用于快速恢复单个 Vault 文件。
2. Ubuntu 每小时创建 Vault、数据目录和服务器配置的一致性归档，校验清单、SHA-256 和所有 SQLite 数据库完整性。
3. Windows SYSTEM 任务把最新完整归档复制到第二物理盘 `D:\KnowledgeManagerBackups` 并再次核对大小和 SHA-256。

Syncthing 副本不等于备份，第二物理盘与 Ubuntu 仍在同一台旧笔记本内。该设计可应对主盘、虚拟机或误操作，但不能应对整机丢失、火灾或两块盘同时损坏。以后增加一块定期断开的加密 USB 盘时，沿用受限只读导出协议；这项物理介质增强不作为当前已具备能力声称。

### 6.2 一致性与保留

备份开始时依次暂停公网微信入口、Syncthing 和主应用，确认所有写入者停止后再归档；完成、失败或可处理的取消后，只恢复备份前正在运行的服务，顺序为主应用、Syncthing、微信入口。强制断电后的开机检查必须识别未恢复的服务状态。

自动保留最近 24 个小时恢复点、30 个每日恢复点和 12 个每周恢复点；升级前归档单独标记，不被普通保留清理删除。保留算法只操作带受管标记、通过命名及清单校验的归档目录，删除前确保至少一个最新完整归档及一个已复制到第二盘的完整归档仍存在。

每月从第二物理盘副本恢复到新的独立目录，验证清单、散列、SQLite `integrity_check`、条目/任务数量、中文 Markdown、附件链接和抽样原件字节。演练不覆盖生产目录，也不自动切换服务。

## 7. 错误处理和可观测性

健康状态分别报告主应用、存储、DeepSeek 配置、微信 worker、回调隧道、Syncthing 和最近备份；“配置完成”与“真实验收通过”使用不同状态。任何单项失败不能让总体页面错误显示全部可用。

日志使用任务 ID、消息 ID 的不可逆短标识、错误类别和耗时关联流程；正文、转写、API 密钥、微信密钥、回调查询参数和 Authorization 头不得进入日志。任务失败时保留原件和已完成的阶段结果，支持安全重试；用户可从微信简短错误或管理页面看到下一步，而不会收到内部路径或堆栈。

## 8. 实施顺序

1. 将本设计提交 GitHub，用户审核后编写分步实施计划。
2. 先实现并测试 DeepSeek 提供方、长文证据校验和失败重试，替换本地 LLM 运行依赖但保留默认关闭门槛。
3. 实现可重复执行的 Tailscale/Syncthing 安装与配置、忽略规则、冲突检查和服务状态检查。
4. 扩展一致性备份以暂停 Syncthing，实现分层保留和月度恢复检查。
5. 在 Ubuntu 部署同步端，实际连接 Windows；再由用户在安卓完成 Tailscale、Syncthing-Fork 和 Obsidian 的必要交互配置。
6. 用真实 DeepSeek API 密钥完成质量、故障与成本验收，通过后启用 AI。
7. 用用户的 Cloudflare 域和微信客服账号配置公网入口，完成真实端到端收发。
8. 执行 Ubuntu、Windows 宿主和客户端重启、断线重连、冲突、备份及恢复综合验收。
9. 把所有代码、测试、运维文档和脱敏验证记录提交现有分支，确认 GitHub Windows/Linux CI 与本地代码树一致。

## 9. 完成标准

以下条件必须全部具备权威证据，项目才可称为完成：

- 微信真实提交全部约定格式并收到结果；原件、正文、转写、DeepSeek 分析、数据库和 Obsidian 笔记一致，重复消息不重复入库。
- DeepSeek 长文测试覆盖开头、中间和结尾强制事实，结构、证据、超时、限流、鉴权失败及重启续处理均符合设计。
- Windows 和安卓 Obsidian 完成双向往返、离线重连、冲突保留、误删恢复和三端散列收敛。
- Ubuntu 重启后应用、Syncthing、备份、微信回调和 Cloudflare Tunnel 按配置恢复；未配置服务保持关闭。
- 公网只能到达微信回调，管理 API、SSH、Syncthing、Vault、数据库和凭据不能经公网域名访问。
- 每小时归档、第二物理盘复制、分层保留及从第二盘独立恢复均通过；同机双盘风险继续明确记录。
- GitHub 远端包含全部实现与脱敏验证材料，CI 通过，部署 release 对应的源码树可追溯；仓库不含知识内容或任何真实凭据。

任何缺少真实账号、域名、API 密钥、安卓端操作或验收证据的项目只能标记为相应阶段未完成，不能用模拟测试或配置文件存在代替。
